## 這章在講什麼

前面 00–05 是 Redis 的「能力」（資料結構、鎖、過期）。**06 是「用這些能力解真實系統問題」**。四大主題：

```
請求進來
  → §3 限流（第一道閘門，超額直接拒絕，保護後面）
  → §4 認證（token / JWT 驗身分）
  → §2 快取（擋在 DB 前，減壓 + 防四大問題）
  → DB
其他：§5（分散式 ID / 延遲隊列 / 排行榜 / 事件）視業務加掛
```

Redis 在應用層的角色：**擋在核心系統前的「多功能瑞士刀」**——限流、認證、快取、計數、隊列全包。

## §2 快取四大問題

大前提：**Redis 當快取，擋在 DB 前面**。命中 → 微秒回、不碰 DB；miss → 回源 DB（慢）→ 回填。這四個問題都是「用快取」這個架構衍生的。

| 問題 | 白話 | 誰受害 | 解 |
| --- | --- | --- | --- |
| **穿透** Penetration | 查**根本不存在**的資料，每次都 miss、每次打 DB | 惡意亂猜 id / 掃描 | 空值快取 + 布隆 |
| **擊穿** Breakdown | **單一熱 key** 過期瞬間，大量請求同時 miss 打 DB | 首頁/爆款商品 | 互斥鎖重建 + 邏輯過期 + singleflight |
| **雪崩** Avalanche | **大量 key** 同時過期，DB 瞬間被打爆 | 一批快取同時到期 | TTL 抖動 + 熔斷 |
| **一致性** Consistency | DB 改了、快取還是舊的 → 讀到髒資料 | 任何有寫入的資料 | Cache Aside（先更 DB、後刪 cache）+ 延遲雙刪 |

差別關鍵：**穿透=資料不存在**、**擊穿=資料存在但單一熱 key 剛過期**、**雪崩=很多 key 一起過期**。

### 2.1 穿透 → 空值快取 + 布隆

- **空值快取**：DB 也查無時，往快取塞哨兵 `__NULL__` + 短 TTL。下次同 id 命中哨兵直接擋，不打 DB。**連「查無」都快取起來**。
- **布隆過濾器**：查之前先問「這 id 可能存在嗎？」。**無 false negative**（說沒有就一定沒有 → 可安全擋），有 false positive（放行後靠空值快取兜底）。用極小記憶體（bitmap）攔大量亂打。
- **分工**：布隆擋「從沒存在過」的、空值快取擋「查過確認不存在」的。
- 對照 `labs/06` §1、§2（bitmap 自建布隆）。

### 2.2 擊穿 → 互斥鎖重建（三種解法）

1. **互斥鎖重建**（最直觀）：miss 時搶「重建鎖」（`SET NX PX`），**只有搶到的查 DB 回填**，其餘 backoff 後重讀快取。用 Stage 5 的鎖。
2. **邏輯過期**（讀不阻塞）：key **不設 TTL**，value 裡塞 `expireAt`。讀到「邏輯過期」→ **先回舊值**，同時背景拿鎖重建。優點：讀永不阻塞、永遠有值可回；缺點：短暫讀到舊資料。
3. **singleflight**（單機合併）：同一 Go 行程對同一 key 的並發回源合併成**一次** DB 查詢。

> **生產最佳實踐 = singleflight（擋單機並發）+ 分散式鎖（擋跨機並發）+ TTL 抖動（防雪崩）三者合體。** 兩層鎖各司其職：singleflight 把每個 Pod 壓成一次，分散式鎖把 N 個 Pod 壓成全叢集一次。
> 對照 `labs/06` §3（互斥鎖重建 + double-check + TTL 抖動）。

### 2.3 雪崩 → TTL 抖動

- **問題**：大量 key 設一樣的 TTL → 整齊地同時過期 → 那一瞬間全 miss 一起打 DB。
- **解**：TTL 加隨機抖動（`base + rand`），讓到期時間錯開。
- 加分：配**熔斷**——DB 撐不住時 fail fast 回降級值，別讓查詢繼續堆積壓垮 DB。
- 對照 `labs/06` §4（用 PTTL 分佈證明：固定 TTL 全擠一桶、抖動後分散）。

### 2.4 一致性 → Cache Aside（重點展開）

**問題**：資料同時在 DB 和 Redis 兩處。只要「雙寫」就有時序問題，**做不到強一致**，只能追求「**最終一致 + 不一致窗口盡量小**」。

**業界標準：Cache Aside（旁路快取）**
```
讀：先讀 cache，miss 才讀 DB 並回填
寫：先「更新 DB」，再「刪除 cache」（不是更新 cache）
```

**四個為什麼（面試高頻，逐一拆）**：

**① 為什麼寫是「刪」不是「更新」cache？**
- **省算力**：寫完不一定有人讀，重算 cache 白費。刪除採 lazy——下次真有人讀才重建。
- **避免並發寫覆蓋**：兩並發寫 A、B。若「更新 cache」，DB 順序和 cache 順序可能不一致（A 先寫 DB、B 後寫 DB，但 B 先更 cache、A 後更 cache）→ cache 留下 A 的舊值（髒）。刪除沒這問題，下次讀從 DB 拉最新。

**② 為什麼「先更 DB、後刪 cache」不是「先刪 cache、後更 DB」？**

先刪 cache 後更 DB 的並發災難：
```
T1: 刪 cache
T2: 讀 cache(miss) → 讀 DB(舊值) → 回填 cache(舊值!)
T1: 更新 DB(新值)
→ cache 舊、DB 新，長期不一致（直到 TTL）
```
改成先更 DB 後刪 cache，窗口小很多：
```
T1: 更新 DB(新值) → 刪 cache
T2: 讀 cache(miss) → 讀 DB(新值) → 回填 cache(新值) ✓
```

**③ 先更 DB 後刪 cache 還是有極小窗口**：
```
T2: 讀 cache(剛好 miss) → 讀 DB(舊值)
T1: 更新 DB(新值) → 刪 cache
T2: 回填 cache(舊值!)
```
要湊齊「讀的 DB 查詢早於寫、但 cache 回填晚於刪除」很難（讀通常比寫快），機率極低。要更保險 → 延遲雙刪。

**④ 延遲雙刪（Delayed Double Delete）**：
```
刪 cache → 更 DB → 睡一小段(500ms~1s) → 再刪一次 cache
```
第二刪清掉「更 DB 期間被其他讀請求用舊值回填」的殘留。睡的時間要略大於「一次讀操作耗時」。**務必放背景 goroutine + 獨立 context**，別阻塞主流程。

**兩個保命底線**：
- **刪快取失敗要重試**（binlog 訂閱如 Canal / 訊息隊列），別 fire-and-forget 就當成功 → 否則髒資料殘留。
- **所有 cache key 都要有 TTL 兜底**——就算刪除全失敗，TTL 到了也自動修正。這是最終一致的最後保險。

**心法**：快取一致性只能做「最終一致」，接受短暫不一致，用「先更 DB 後刪 cache + 延遲雙刪 + 短 TTL」把窗口壓到最小。要強一致就別用快取。

## §3 限流四算法

### 3.0 總綱（先建立定位）
- **限流是「進入系統的第一道閘門」**——保護層、非業務邏輯。擋最前面，超額直接拒絕，保護後面 DB/服務。
- **全域桶 vs per-user 桶**：全域保護系統總量；per-user 防單一用戶刷爆（key 帶 userId）。
- **為什麼要 Redis**：多台服務器共享同一計數 → 狀態放 Redis（分散式限流）。單機用 `x/time/rate` 即可。
- **穩定性四件套**：限流（擋量）/ 熔斷（斷開故障依賴）/ 降級（回退）/ 快取（減壓）。
- **限流 vs MQ 削峰別搞混**：限流超額**拒絕**（fail fast）；MQ 削峰超額**排隊**慢慢處理（不拒絕）。

### 四個算法

| 算法 | 核心 | 優點 | 坑 | 何時用 |
| --- | --- | --- | --- | --- |
| **固定窗口** | 每分鐘一計數器 `INCR`+`EXPIRE` | 最簡單 | **邊界突刺**：窗口交界瞬間可過 2 倍量 | 精度要求低 |
| **滑動窗口** | ZSet 存每次請求時間戳，移除窗口外的、數剩幾個 | 精確、無邊界問題 | 存每筆請求較耗記憶體 | 要精確 |
| **令牌桶 ★最推薦** | 桶固定速率補 token，來請求拿一個、沒 token 拒絕 | **容忍突發**（桶有存量）+ 平均限速 | Lua 稍複雜 | 通用首選 |
| **漏桶** | 請求進桶，固定速率漏出 | **強制平滑**輸出 | 不容突發 | 要平穩輸出、對下游友善 |

**令牌桶為何最推薦**：兼顧「平均限速」+「容忍短暫突發」（桶裡攢的 token）。用 **Lua** 做到「取 token + 補 token + 判斷」原子化（**惰性補充**：不用背景 timer，取的時候依時間差算該補多少）。

**令牌桶 vs 漏桶關鍵差**：令牌桶**允許突發**（桶滿能一次噴一批）對用戶友善；漏桶**強制平滑**（出口固定速率）對下游友善。

**reject vs wait**：限流該「超額拒絕」，不是「排隊等」（排隊是 MQ 的事）。

**不想自己寫 Lua**：`x/time/rate`（單機）或 redis-cell 的 `CL.THROTTLE`（分散式、內建 GCRA）。

對照 `labs/01-string-counter`（令牌桶 demo）。

## §4 Token / 認證

| 模式 | 核心 | 取捨 |
| --- | --- | --- |
| **4.1 Session token** | `token → userID` 存 Redis + TTL；登入寫、驗證查、登出刪 | 有狀態、**可即時撤銷**；每次驗要查 Redis |
| **4.2 JWT 黑名單** | JWT 無狀態不能撤銷 → 撤銷時把 `jti` 加進 Redis 黑名單，TTL = token 剩餘壽命 | 解「JWT 簽發後無法作廢」；過期自動清 |
| **4.3 Refresh 輪換 + 重放偵測** | 每次刷新**刪舊發新**（原子 Lua）；舊 token 又被用 → 偵測到重放（被盜）→ 全作廢 | 防 refresh token 被偷：一次性 + 重放告警 |

**核心對比**：session token（有狀態、可即時撤銷、驗證要查庫）vs JWT（無狀態、驗證免查庫、撤銷難→靠黑名單補）。

## §5 其他實用模式（各一句）

| 模式 | 核心 |
| --- | --- |
| **分散式 ID**（INCR 分段發號）| 一次領 1000 個（回末尾值），本地慢慢用 → 減少 Redis 往返 |
| **延遲隊列**（ZSet score=時間戳）| 撈 `score <= now` 的到期任務（延遲取消訂單、定時任務）|
| **排行榜**（ZSet）| `ZADD` 計分、`ZREVRANGE` 分頁取排名 |
| **布隆**（模組 vs 自建）| 沒 RedisBloom 模組就用 SETBIT/GETBIT 自己做（`labs/06` 就這樣）|
| **Pub/Sub vs Stream** | Pub/Sub 發後即忘（沒人收就丟）；Stream 持久化 + 消費者群組 + ack |
| **分散式 Session** | Redis 存 session，多台服務器共享登入狀態 |
